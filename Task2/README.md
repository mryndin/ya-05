# Отчет по Задаче №2: Проверочный лист безопасности бизнес-систем PropDevelopment

**Объект:** Группы сервисов «Продажи», «ЖКУ», «Финансы» и «Дата»  
**Статус:** Выполнение Task2  

---

## 1. Обоснование выбора разделов проверочного листа

Для формирования чек-листа выбраны 5 приоритетных разделов, которые напрямую связаны с текущими инцидентами и стратегическими планами компании:

### 1.1 Управление доступом (IAM) — Приоритет: КРИТИЧЕСКИЙ
**Почему включено:** Клиенты видят чужие ФИО в личных кабинетах. У каждого приложения своя точка входа (auth-service-1 только для витрины, client-crm-app и tenant-core-app используют отдельные механизмы). Это создает дубликаты учетных записей и риски перекрестного доступа.

### 1.2 Безопасность данных — Приоритет: КРИТИЧЕСКИЙ
**Почему включено:** Проведение онлайн-сделок накладывает требования 152-ФЗ. Внутренние потоки данных между IT-продуктами контролируются не системно. Со стороны систем обработки данных (BI/Дата) нет ограничений на доступ к ПДн.

### 1.3 Безопасность инфраструктуры — Приоритет: ВЫСОКИЙ
**Почему включено:** Гибридная инфраструктура (собственный ЦОД + облако) увеличивает поверхность атаки. Услуга «Умный дом» создает риски физической безопасности при компрометации IoT-контуров.

### 1.4 Управление инцидентами — Приоритет: ВЫСОКИЙ
**Почему включено:** После утечки у конкурента руководство обеспокоено. Один специалист по ИБ на компанию, процесс передачи информации нарушен. Нет формализованного плана реагирования.

### 1.5 Процессы ИБ — Приоритет: СРЕДНИЙ, но фундаментальный
**Почему включено:** Специалист по ИБ исключен из процесса принятия архитектурных решений. Без исправления этого процесса любые технические меры будут временными.

## 2. Проверочный лист безопасности

| № | Вопрос | Да/Нет | Комментарий |
|---|--------|--------|-------------|
| **I. Управление доступом** | | | |
| 1 | Используется ли единая система аутентификации (IdP) для всех клиентских приложений? | Нет | auth-service-1 (Keycloak) используется только для витрины продаж. client-crm-app, tenant-core-app и accountant-service-1 используют отдельные механизмы. Это создает дубликаты учетных записей и риски перекрестного доступа. |
| 2 | Реализована ли строгая изоляция сессий (предотвращение перекрестного доступа к данным)? | Нет | Есть подтвержденные жалобы: клиенты видят чужие ФИО в личных кабинетах. Требуется внедрение Row-Level Security на уровне БД. |
| 3 | Реализован ли принцип минимальных привилегий для доступа к CRM-системам? | Нет | Со стороны систем обработки данных (BI/Дата) ограничения на доступ отсутствуют. Аналитики имеют прямой доступ к сырым данным из всех БД. |
| 4 | Ведётся ли журналирование всех операций доступа к системам и данным? | Неизв. | Требуется аудит: какие события логируют client-crm-app, tenant-core-app, auth-service-1. Нет централизованного сбора логов (SIEM). |
| 5 | Автоматически ли деактивируются учётные записи после увольнения сотрудников? | Неизв. | Аккаунты менеджеров и бизнес-аналитиков управляются через Active Directory. Требуется проверить интеграцию с HR-системой. |
| 6 | Ведётся ли единый реестр учётных записей? | Нет | Учетные записи дублируются в auth-db-1, crm-db, tenant-core-db. Нет единого источника истины. |
| **II. Безопасность данных** | | | |
| 1 | Разработана ли политика классификации данных? | Нет | Нет формализованной классификации (публичные/внутренние/конфиденциальные/секретные). ПДн не маркируются при создании. |
| 2 | Используется ли шифрование данных при передаче по сети? | Неизв. | Требуется проверить: client-mart-app → Госорганы (СМЭВ, SOAP), tenant-core-app → Платёжная система, все CDC-пайплайны в Greenplum. |
| 3 | Используется ли шифрование данных на уровне БД (at-rest)? | Неизв. | Требуется проверить настройку TDE для: crm-db (MSSQL), tenant-core-db (PostgreSQL), client-mart-db, auth-db-1. |
| 4 | Проводится ли регулярное резервное копирование данных? | Да | Согласно описанию, для всех БД выполняется резервное копирование на глубину, необходимую для восстановления. |
| 5 | Выполняется ли тестирование восстановления из резервных копий? | Неизв. | Наличие бэкапов ≠ возможность восстановления. Требуется проверить процедуру и частоту DR-тестов. |
| 6 | Ограничен ли доступ к резервным копиям, и зашифрованы ли они? | Неизв. | Критично для БД с ПДн. Требуется аудит прав доступа к хранилищам бэкапов в ЦОД и облаке. |
| 7 | Ведётся ли учёт персональных данных и применяются ли спецпроцедуры для их обработки? | Нет | Нет реестра операций с ПДн. Неясно, где именно хранятся паспортные данные, ИНН, платежные реквизиты. |
| 8 | Осуществляется ли мониторинг доступа к данным на основе их классификации? | Нет | Нет меток безопасности. Нет алертов на аномальный доступ к ПДн (например, массовая выгрузка из crm-db). |
| 9 | Реализованы ли процессы анонимизации данных для тестовых сред? | Нет | Разработчики могут иметь доступ к прод-подобным данным без маскирования ПДн. |
| **III. Безопасность инфраструктуры** | | | |
| 1 | Используется ли межсетевой экран для ограничения трафика? | Да | Указано в описании: доступ внешних пользователей осуществляется через firewall. Требуется аудит правил фильтрации. |
| 2 | Реализована ли сегментация сети на логические зоны (DMZ, App, Data)? | Неизв. | Критично для изоляции контура «Умный дом». Требуется проверить: отделен ли IoT-трафик от публичного, есть ли микросегментация между доменами. |
| 3 | Используются ли IDS/IPS-системы для обнаружения атак? | Неизв. | Требуется проверить наличие и настройку систем обнаружения вторжений на периметре и внутри сети. |
| 4 | Проводится ли регулярное сканирование уязвимостей ОС и приложений? | Неизв. | При гибридной инфраструктуре (ЦОД + облако) риск конфигурационных ошибок возрастает. Требуется автоматизация сканирования. |
| 5 | Отключены ли неиспользуемые службы и порты на серверах? | Неизв. | Требуется аудит базовых образов ОС и конфигураций контейнеров для всех сервисов. |
| 6 | Осуществляется ли фильтрация трафика между сетевыми сегментами? | Неизв. | Особенно важно для трафика между доменами (Продажи ↔ ЖКУ ↔ Финансы) и для интеграций с партнерами. |
| **IV. Управление инцидентами** | | | |
| 1 | Используется ли SIEM-система для корреляции событий? | Нет | Логи разрознены по системам. Нет единой панели для обнаружения аномалий в реальном времени. |
| 2 | Настроены ли автоматические оповещения о подозрительной активности? | Неизв. | Требуется проверить: алерты на множественные неудачные логины, массовую выгрузку данных, доступ из необычных локаций. |
| 3 | Разработан ли план реагирования на инциденты (IRP)? | Нет | Процесс не формализован. Нет процедур эскалации, изоляции, восстановления. Специалист по ИБ один. |
| 4 | Проводятся ли учения по реагированию на инциденты? | Нет | Команды не тренируются на сценариях утечки ПДн или компрометации инфраструктуры. |
| 5 | Как часто проводятся аудиты безопасности? | Неизв. | Компания готовится к комплексному аудиту — это первое крупное мероприятие. Требуется установить регулярность. |
| **V. Процессы ИБ** | | | |
| 1 | Участвует ли специалист по ИБ в согласовании архитектуры новых сервисов? | Нет | Процесс передачи информации нарушен. ИБ-специалисту передают не все решения. Архитектурные ревью проходят без оценки рисков. |
| 2 | Проводится ли обучение сотрудников по основам ИБ? | Нет | Менеджеры, бизнес-аналитики и разработчики не проходят регулярное обучение по 152-ФЗ и безопасному кодированию. |
| 3 | Ведётся ли реестр активов и данных? | Нет | Нет инвентаризации: где хранятся ПДн, какие системы обрабатывают конфиденциальные данные, кто имеет доступ. |
| 4 | Документированы ли политики и процедуры ИБ? | Неизв. | Требуется проверить наличие: политики обработки ПДн, регламента доступа, инструкции по реагированию на инциденты. |

## 4. Рекомендации по результатам проверки

### 4.1 Немедленные действия (0-2 недели) — блокирующие риски
1. **Исправить уязвимость перекрестного доступа (I.2)**: внедрить Row-Level Security во всех БД с ПДн (crm-db, tenant-core-db, client-mart-db). Проверить каждый запрос на наличие фильтра `WHERE user_id = current_user`.
2. **Аудит интеграций с партнерами**: составить реестр всех API-контрактов с УК, проверить наличие избыточных ПДн в ответах, отозвать «широкие» ключи доступа.
3. **Включить логирование операций с ПДн (I.4)**: кто, когда, к каким данным обращался. Интегрировать с централизованным хранилищем логов.

### 4.2 Краткосрочные действия (1-3 месяца)
1. **Внедрить единый IdP (I.1)**: расширить использование auth-service-1 (Keycloak) на все клиентские приложения. Реализовать OAuth 2.0 / OIDC.
2. **Разработать политику классификации данных (II.1)**: утвердить 4 категории (публичные/внутренние/конфиденциальные/секретные), внедрить автоматическое обнаружение ПДн.
3. **Назначить Security Champion в каждую команду (V.1)**: обучить разработчиков основам ИБ, наладить коммуникацию со специалистом по ИБ.
4. **Разработать план реагирования на инциденты (IV.3)**: зафиксировать роли, тайминги, процедуры эскалации и восстановления.

### 4.3 Среднесрочные действия (3-6 месяцев)
1. **Внедрить SIEM (IV.1)**: централизованный сбор и корреляция логов, алерты на аномальную активность.
2. **Автоматизировать сканирование уязвимостей (III.4)**: интеграция в CI/CD, регулярное сканирование образов и зависимостей.
3. **Подготовить документацию для 152-ФЗ**: УПД, модель угроз, реестр операций с ПДн.

## 5. Приложения

| Система | Тип | Технология | Критичность |
|---------|-----|------------|-------------|
| auth-service-1 | Сервис аутентификации | Keycloak | 🔴 Критическая |

### 5.2 Глоссарий
- **ПДн** — персональные данные (152-ФЗ)
- **IdP** — Identity Provider, поставщик идентификации
- **RLS** — Row-Level Security, безопасность на уровне строк БД
- **SIEM** — Security Information and Event Management
- **CDC** — Change Data Capture, механизм репликации изменений
